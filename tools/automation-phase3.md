## 1. 병목 ① 로그인 쿠키 — 세 갈래와 권장안

> ⚠️ **정정 (2026-09-06 실측)**: 이 절의 전제 — "수강편람 내부 API 는 학사 계정 세션이 있어야
> 응답한다" — 는 **틀렸다.** Cookie 헤더를 전혀 보내지 않아도 마일리지 요약(1행)·순위(83행)·
> 대학/학과 코드·과목 목록(기계공학전공 2026-2, 33분반)이 전부 정상 JSON 으로 온다. 무효
> JSESSIONID 로도 동일. 과거 "쿠키 만료 → HTML" 은 로그인이 아니라 **게이트**(수강신청 기간의
> NetFunnel 대기열·점검·WAF)였을 가능성이 크다. 따라서 병목 ① 은 사실상 없고, 쿠키는 게이트가
> 켜진 기간에 통과용으로만 남긴다(선택). 아래 A/B/C 갈래와 P3-0 의 원래 판정 문구는 기록으로
> 남기되, 결론은 이 정정이 우선한다.

수강편람 내부 API 는 학사 계정 세션(`JSESSIONID`)이 있어야 응답한다고 **가정했었습니다**(위 정정
참조). 자격증명·쿠키는 공개 저장소·Actions Secrets 에 둘 수 없다는 원칙(계획서 2절 4)은 그대로입니다.

| 갈래 | 내용 | 장점 | 위험·비용 | 판정 |
| --- | --- | --- | --- | --- |
| **A. 세션 유지(keep-alive)** | 사람이 학기에 한 번 로그인하면, 로컬 데몬이 10분마다 가벼운 API(학기 목록 조회)를 호출해 세션을 살려 둔다 | 코드 반나절, 계정 위험 없음, 서버 부하 무시 가능(시간당 6요청) | 만료가 **무활동 타임아웃**이어야만 성립. 절대 만료(SSO 토큰 수명)면 무효. 서버 재시작·학교 정책으로 끊길 수 있음 | **실험 후 결정** (P3-0) |
| **B. 학교 협의** | 학과 행정을 통해 정보화 부서에 읽기 전용 계정 또는 데이터 제공(CSV·API)을 요청 | 정공법, 장기적으로 유일하게 깨끗한 해법 | 기간·성사 불확실, 담당자 노력 | **병행 추진** (P3-6) |
| **C. SSO 자동 로그인** | headless 브라우저로 ID/PW 입력 | 완전 무인 | 계정 잠금, 약관 위반 가능, NetFunnel 대기열, 비밀번호 보관, 실패 시 복구 비용이 이득보다 큼 | **비권장 유지** — 별도 계정 + 학교 승인 시에만 재검토 |

### P3-0 세션 수명 실험 (0.5일 · 사람 로그인 1회) — ⚠️ 판정 철회 → **세션 불필요 (2026-09-06 재실측)**

> ⚠️ 아래 "65시간 생존" 판정은 **무효**다: 데몬이 핑에 쓴 학기 목록 API 가 쿠키 없이도 같은 JSON 을 주는
> 엔드포인트라, 잰 것은 세션이 아니라 서버 생존이었다(Worker G 발견 → Advisor 재실측으로 확정). 이후
> Cookie 없이 요약·순위·과목 목록까지 정상임을 확인해 결론은 "세션 자체가 필요 없다" 로 바뀌었다.
> 데몬은 세션 감시가 아니라 **포털 응답 감시**(비정상이면 이슈, 정상 복귀 시 자동 재개)로 재정의한다.
>
> (기록) 실측: 9/3 21:44 KST 이전에 받은 쿠키가 9/6 15:04 KST 핑에 정상 응답 — 65시간 이상 생존. 그 사이
> 데몬이 세션 종료로 멈춰 **9/4 17:06 UTC 부터 37시간 동안 요청이 하나도 없었는데도** 살아 있었다
> (핑 30회 ok · 만료 0 · 일시 네트워크 오류 5). 즉 만료는 짧은 무활동 타임아웃도, 수 시간짜리 절대
> 만료도 아니다 — 세션은 며칠 단위로 산다(상한은 미측정: 서버 재시작·학교 정책이 끊을 때까지).
> 결론: **학기 초 로그인 1회로 크롤 창을 충분히 덮는다.** keep-alive 데몬은 세션 연장 장치라기보다
> **죽음 감지 + 로그인 요청 이슈** 역할로 남긴다(P3-3 에서 상시 서비스로). README 의 "수 시간 만료"
> 는 크롤 중 관측된 다른 원인(NetFunnel·서버 재시작)이었을 가능성이 크다.

1. 로그인 → 쿠키를 로컬 데몬(`tools/automation/session-keepalive.mjs`, 크롤러 `api.js`
   재사용)에 넣는다. 데몬은 10분마다 `findMlgSyySmtDivCdList` 를 1회 호출하고 응답이 JSON 인지
   기록한다(`.state/keepalive.log`).
2. 24시간·72시간 시점의 생존 여부로 판정한다.
   - **살아 있음** → 만료는 무활동 기준. A 채택: 학기 초 로그인 1회로 학기 전체를 덮는다.
     데몬이 죽음을 감지하면 이슈 `[자동] 수강편람 로그인 필요` 를 만들고 이후 단계는 대기.
   - **죽음** → 절대 만료. A 폐기, 현 반자동(리마인더 → 로그인 → 실행) 유지 + B 추진.
3. 매너: 요청 1개/10분, 식별 가능한 UA, 학교 측 요청이 있으면 즉시 중단. 크롤 자체는
   기존 매너 규칙(순차·300ms) 그대로.

> 이 실험이 Phase 3 전체의 분기점입니다. 성공하면 2·3 은 "학기 1회 로그인" 만 남고,
> 실패해도 아래 ②③ 은 그대로 유효합니다(사람 시간의 대부분은 ②③에 있습니다).

`professor-history.csv` 가 수기인 이유는 **과거 학기 라인업을 크롤 시점에 기록하지 않았기

있으므로, 오케스트레이터 ⑤ 단계에서
`(year, semester, code, division, professor)` 를 CSV 에 자동 append 하면 다음 학기부터는
보강이 필요 없습니다(이미 있는 행은 건너뜀, 사람이 적은 행은 우선). `RECENCY_ALIAS` 는
특정 학기 라인업의 예외 보정이라 자동화하지 않고, 값이 남아 있으면 ⑩ 에서 "재검토" 한 줄만
찍습니다.

### P3-5 (조건부) 자동 머지 (S · 운영 실적 후)

두 달 이상 PR 이 문제없이 머지되면, **위험이 낮은 변경 등급**만 자동 머지를 허용합니다:
기존 이벤트의 `lines` 문구 변경(시각·장소)이고 이벤트 추가·삭제·트랙 변경이 없는 PR.
그 외는 계속 사람 머지. 자동 머지도 typecheck 등 CI 통과가 조건입니다.

### 연 1회 전면 재작성의 자동화

새 학년도 캘린더가 게시되면(모집요강 공표 후 4~6월) 워커가 `s_year=YYYY+1` 의 이벤트 수
증가를 감지합니다. 그때 `calendar.year`·`intro` 의 연도를 바꾸고 이벤트를 새 학년도로 채운
**전환 PR** 을 자동 생성합니다. 4/25 리마인더 이슈는 이 PR 이 뜨면 자동으로 닫습니다.

### 이 단계가 끝난 뒤 사람이 하는 일

PR 머지(P3-5 후에는 저위험 변경은 그것도 없음), 미대응 트랙(정시·편입 등 우리 범위 밖)
편입 여부 판단.

## 8. P3-7 구 게시판 신규 글 동기화 (컷오버 전 한시) — 2026-09-07 구현

계획 밖에서 생긴 항목입니다. 위 1~7절이 다루는 세 데이터와 달리 **컷오버 날 사라지는**
한시 루틴이라 번호를 뒤에 붙였습니다.

**문제.** 도메인 컷오버(DNS 가 `me.yonsei.ac.kr` 을 우리 Vercel 로 돌리는 날) 전까지 학과
담당자는 여전히 **구 사이트**에 글을 올립니다. 그동안 우리 사이트의 공지가 며칠씩 비면
"새 사이트는 공지가 늦다" 가 됩니다. 전수 이전(3,544건)은 끝났지만 그건 스냅샷입니다.

**하는 일.** `tools/automation/board-sync.mjs` — 작업 스케줄러 `yonsei-me board-sync`
(매일 04:30, 2시간 상한, WakeToRun 없음).

| 단계 | 내용 |
| --- | --- |
| ① 잠금·로그 | `.state/board-sync.lock`(12시간 유물 정리) · `.state/board-sync-<날짜>.log` tee |
| ② 크롤 | `crawl-boards.mjs --since=<오늘-45일>` — 게시판 전부 "목록 0건" 이면 실패(컷오버 신호) |
| ③ 후보 | `tools/boards-raw/*.json` 중 **최근 60일** 글. 날짜·sourceUrl 없는 글은 제외·경고 |
| ④ DB 확인 | REST 로 `source_url` 존재 조회(50건 배치, 읽기 전용) + **센티널 3건** 검증 |
| ⑤ 신규 | DB 에 없는 글. 0건이면 종료. `--max-pending`(100) 초과면 실패 |
| ⑥ 부분집합 | `.state/board-sync/pending/<board>.json` — **신규 글만** 담은 스냅샷 |
| ⑦ 적재 | `import-boards --input=<그 디렉터리> --apply` → `mirror-legacy-assets --apply` → `rewrite-legacy-links --apply` → `backfill-attachment-sizes --write` |
| ⑧ 검증 | 넣은 `source_url` 이 전부 DB 에 보여야 성공 |

플래그: `--dry-run`(⑥까지 하고 표만) · `--skip-crawl` · `--state-dir <경로>` ·
`--since-days N`(기본 45) · `--max-pending N`(기본 100). 종료 코드는 **0 = 성공·보류·신규
없음**, **1 = 실패**. 실패는 `[자동] 구 게시판 동기화 실패 (<날짜>)` 이슈(issue.mjs 중복 방지).
상태는 `.state/board-sync.json`(`lastRunAt`·`lastSuccessAt`·`lastImported`·`deferred` +
누적 `imported` 최근 500건).

**설계 제약 세 가지 — 여기서 사고가 난다**

1. **신규 글만.** 기존 글의 수정·삭제·상단고정 변경은 동기화하지 않습니다. 적재된 글은 이미
   R2 미러링·링크 재작성을 거쳤는데 원문으로 덮으면 그 가공이 통째로 되돌아갑니다. 그래서
   `import-boards` 에 전체 스냅샷이 아니라 **부분집합 JSON** 을 넘깁니다.
2. **센티널 가드.** REST 가 빈 배열을 주면(권한 상실·URL 오타·프로젝트 정지) 3,500건이 전부
   "신규" 로 보여 **전량 재적재**가 됩니다. 가장 오래된 학부공지 3건을 따로 물어보고 하나라도
   없으면 그 자리에서 멈춥니다.
3. **HTTP 402 는 실패가 아니라 보류.** Supabase egress 초과로 프로젝트가 제한되면 PostgREST 가
   402 를 줍니다(2026-09-06 실측). 이때는 이슈를 만들지 않고 `deferred: true` 만 남기고
   exit 0 — 제한이 풀리면 다음 실행이 같은 글을 그대로 집어 갑니다.

**사이트 반영 시점.** 적재 즉시가 아닙니다. 목록 캐시 수명이 하루라(`fd3427d`, egress 절감)
**최대 24시간 뒤**에 보입니다. 급하면 Vercel 재배포로 앞당깁니다.

**해제 절차 (컷오버 날 반드시)**

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools/automation/register-tasks.ps1 -Unregister -Only board-sync
```

그 뒤 `tools/crawl-boards.mjs` 는 다시 아카이브 도구로 은퇴하고, 게시판 정본은 우리 CMS 하나가
됩니다. `-Only <이름조각>` 은 **돌고 있는 keep-alive 를 건드리지 않으려고** 추가한 필터입니다
(재등록은 실행 중인 작업을 재시작시킵니다).
